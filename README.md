# Вступительное задание: «Платёж прошёл? Докажи»

Нужно собрать небольшой сервис, который проводит платёжную операцию от создания до ответа внешней системы.

Внешнюю систему изображает готовый `provider-simulator`. Сервис должен действительно вызвать его по HTTP, сохранить выданный идентификатор платежа и дождаться асинхронной квитанции. Самостоятельно выставить финальный статус сразу после `submit` недостаточно.

Нам не нужна идеальная архитектура. Важно, чтобы проект собирался, запускался и показывал понятный сквозной результат.

## На чём делать

Используем максимально свежие стабильные версии языков и платформ:

| Вариант | Версия |
|---|---|
| C# | .NET 10 |
| Python | Python 3.14 |

Можно использовать любой удобный фреймворк, базу данных и AI-инструменты.

## Сценарий

```text
создать операцию -> submit -> запрос к provider -> callback-квитанция -> финальный статус
```

У операции достаточно четырёх состояний:

| Состояние | Значение |
|---|---|
| `CREATED` | Операция создана |
| `PROCESSING` | Платёж принят внешней системой в обработку |
| `COMPLETED` | Внешняя система подтвердила успех квитанцией |
| `REJECTED` | Внешняя система отказала квитанцией |

Важно: ответ `202 Accepted` от внешней системы ещё не означает успешный платёж. Переводить операцию в `COMPLETED` или `REJECTED` можно только после callback-квитанции.

## Минимальный API сервиса

Названия маршрутов можно немного изменить, если смысл сохраняется и точные команды проверки описаны в README.

| Метод | Назначение |
|---|---|
| `GET /health` | Проверить, что сервис работает |
| `POST /operations` | Создать операцию |
| `POST /operations/{id}/submit` | Отправить платёж внешней системе |
| `POST /receipts` | Принять callback-квитанцию внешней системы |
| `GET /operations/{id}` | Получить текущее состояние |

Для операции достаточно следующих данных:

- идентификатор;
- сумма;
- валюта;
- описание;
- текущее состояние;
- `providerPaymentId` после принятия платежа внешней системой.

## Контракт внешней системы

Адрес внешней системы передаётся сервису через переменную `PROVIDER_URL`. В Docker Compose это `http://provider-simulator:8081`.

При вызове `submit` сервис выполняет:

```http
POST {PROVIDER_URL}/payments
Content-Type: application/json
X-Correlation-ID: operation-123
```

```json
{
  "operationId": "operation-123",
  "amount": "1000.00",
  "currency": "RUB"
}
```

Требования к запросу:

- `operationId` непустой, не длиннее 128 символов;
- `amount` — положительная десятичная строка, не более двух знаков после точки;
- поддерживается валюта `RUB`;
- `X-Correlation-ID` можно сформировать самостоятельно и использовать в журналах всей операции.

Успешный ответ внешней системы — `202 Accepted`:

```json
{
  "providerPaymentId": "aa5b7856-e9f2-4fd5-955b-38b1f28d9c57",
  "status": "ACCEPTED"
}
```

После такого ответа сервис сохраняет связь `operationId` с `providerPaymentId`, переводит операцию в `PROCESSING` и возвращает результат `submit`. При сетевой ошибке или неуспешном ответе внешней системы финальный статус выставлять нельзя.

Позже симулятор выполнит `POST` на `http://candidate-service:8080/receipts`:

```json
{
  "providerPaymentId": "aa5b7856-e9f2-4fd5-955b-38b1f28d9c57",
  "operationId": "operation-123",
  "result": "COMPLETED",
  "message": "Payment completed",
  "occurredAt": "2026-07-14T12:00:00Z"
}
```

`result` принимает значение `COMPLETED` или `REJECTED`. Обработчик проверяет связь идентификаторов, меняет состояние операции и отвечает любым HTTP-статусом `2xx` после успешной обработки. Симулятор передаёт в callback тот же `X-Correlation-ID`.

## Docker Compose

В корне решения нужен `compose.yaml` или `docker-compose.yml` с сервисами `candidate-service` и `provider-simulator` в общей сети. Минимальная заготовка:

```yaml
services:
  candidate-service:
    build: .
    environment:
      PROVIDER_URL: http://provider-simulator:8081
    ports:
      - "8080:8080"

  provider-simulator:
    image: ghcr.io/fintech-dev-lab/internship-provider-simulator:v0.1.0
    environment:
      CALLBACK_URL: http://candidate-service:8080/receipts
    ports:
      - "8081:8081"
    depends_on:
      - candidate-service
```

Образ публичный, `docker login` для его скачивания не нужен. Запуск решения должен выполняться одной командой:

```bash
docker compose up --build
```

## Что обязательно

- проект собирается;
- всё решение запускается через Docker Compose;
- сервис кандидата слушает порт `8080`;
- `GET /health` возвращает `200 OK`;
- можно создать операцию;
- `submit` выполняет реальный HTTP-запрос к `provider-simulator`;
- ответ `202 Accepted` переводит операцию только в `PROCESSING` и сохраняет `providerPaymentId`;
- callback-квитанция меняет состояние на `COMPLETED` или `REJECTED`;
- состояние можно получить через API;
- в README есть команды запуска и проверки полного сценария.

Хранилище может быть любым, включая память приложения. Постоянное хранение, тесты, валидация, идемпотентность и история событий приветствуются, но для зачёта не обязательны.

## Как сдать

1. Создайте отдельный публичный репозиторий GitHub.
2. Разместите в нём решение, Dockerfile, Docker Compose и README с командами запуска и проверки.
3. Убедитесь, что репозиторий можно клонировать и запустить на чистой машине по README.
4. В ответ на сообщение с тестовым заданием на hh.ru пришлите ссылку на репозиторий.

Делать fork этого репозитория и открывать pull request не нужно. Репозиторий с решением должен оставаться публичным на время проверки.

## Как проверяем

Оценки по баллам нет. Результат — `зачёт` или `незачёт`.

Для зачёта достаточно, чтобы:

1. `docker compose up --build` скачал симулятор, собрал и запустил решение;
2. `health` сервиса кандидата ответил успешно;
3. базовый путь `создание -> submit -> реальный вызов provider -> callback -> финальный статус` отработал хотя бы один раз;
4. проверяющий смог повторить сценарий по README.

Проверка отдельно убеждается, что внешний запрос действительно был выполнен. Заглушка, которая выставляет `COMPLETED` внутри `submit`, не проходит.

Небольшие недочёты в обработке ошибок или структуре проекта не мешают зачёту, если основной сценарий и внешний контракт работают.

## Что даст преимущество

- состояние переживает перезапуск;
- повторный запрос или callback не создаёт повторный бизнес-эффект;
- есть тесты;
- есть история изменений операции;
- недоступность внешней системы обрабатывается без ложного успеха;
- ошибки возвращаются в понятном формате;
- путь операции собирается по `X-Correlation-ID`.
